# 入库闸门 · memory ingest gate

> **库只装「下次还用得上的判断」，不装过程。**
> 闸门的职责，是把「看起来像结论的东西」逼到**能被检验的形态**，再按证据强弱分流。

给 AI 记忆库 / 知识库用的一道写入闸：不靠提示词、不靠自觉，靠**校验顺序**。

```
校验 → 重复 → 冲突 → 用途 → 等级分流
```

顺序本身就是逻辑：**先判重、再判冲突，最后才谈等级**。反过来会把「重复」当「冲突」塞进队列。

---

## 它解决什么

AI 写记忆最常见的四种坏味道：

| 坏味道 | 闸门怎么挡 |
|---|---|
| 同一个人三种写法，检索全漏 | 实体必须先登记（`_实体表.md`），未登记直接拒 |
| 结论无法回溯，等于道听途说 | `source_ref` 必须能定位到行/事件，否则不收 |
| 重复条目被当成「冲突」 | 先判重（同实体+同关系+同值+区间重叠）→ 拒收并给出已有 id |
| 未证实的东西和已证实的混在一起 | 五档证据等级 + V3 只进候选区 + V4 直接 refuted |

## 60 秒上手

```bash
git clone <this repo> && cd memory-ingest-gate

python3 src/gate.py init --vault vault
python3 src/gate.py entity add E01 "张工" --note "外部联系人"

cat > c.json <<'EOF'
{"layer":"L2","subject":"E01","relation":"认为",
 "object":"批量改名要先按修改时间排序","dimension":"工作方法",
 "valid_from":"2026-11-06","source":"对话","source_ref":"inbox/20261106.md#L12",
 "level":"V1","level_by":"agent","verify":"跑一次改名脚本，输出 3 行新名",
 "use_when":"批量处理发票/照片时"}
EOF

python3 src/gate.py --vault vault add --json c.json
# {"ok": true, "status": "active", "id": "C-20261106-001", "where": "claims"}
```

再提交同一份 → `{"ok": false, "status": "duplicate", "existing": "C-20261106-001"}`。
**闸门不让你重复写，它让你去改那一条。**

自测（不碰你的库）：

```bash
python3 src/gate.py selftest
```

## 一条主张必填七项

| 字段 | 含义 | 不合格 |
|---|---|---|
| `layer` | L0 规则 / L1 证据 / L2 关联 / L3 场景 / L4 项目 / L5 个人 | 不在枚举内拒 |
| `subject` | 实体编号（E01…），必须先登记 | 「实体未登记」拒，并列出已知实体 |
| `relation` | 关系（规定/决定/认为…） | 空即拒 |
| `object` | 值（结论本身） | 空即拒 |
| `valid_from`（+`valid_to`/`precision`） | 有效区间；precision=日/月/年 | 空即拒 |
| `source` + `source_ref` | 来源；**必须能定位**：`inbox/a.md#L12` 或 `event:2026-11-03 21:35` | 定位不到拒 |
| `level` + `level_by` | 证据等级与定级人 | 越权即拒 |

**按类追加两条**

- 规定类必须有 `dimension`（分不清「同一件事的两种说法」还是「并行的两件事」）
- 必须有 `use_when`（将来什么时候会用到）；唯一豁免：`relation=规定 且 level=V0`

---

## 五档证据等级 + 四条硬规则

| 级 | 含义 | 谁能定 |
|---|---|---|
| **V0** | 本人定的规则（宪法级） | **只有本人**；agent 写直接拒 |
| **V1** | 已证实（本机可复现） | agent 可给，但 `verify` 必须写清「怎么跑、输出是什么」 |
| **V2** | 侧面证实（文档/网页/他人转述） | agent 最高到 V2 |
| **V3** | 未证实 | 只进候选区（`N-` 前缀） |
| **V4** | 已证伪 | 状态 `refuted`，检索默认排除 |

1. **V0 只有本人能写**
2. **升级每步只许一级**（V3→V2→V1→V0），跳级直接拒，并告诉你本次最多到哪
3. **降级 agent 一律拒**：只有本人（`--by owner`）能降，同样每步一级，并往条目 `## History` 追加一行
4. **越靠事实越硬，越靠偏好越软**：不能复现的一律降档

---

## 冲突：不静默覆盖

- 同实体 + 同关系 + 同维度 + 值不同 + 区间重叠 → 进 `queue/`
- `condition` 不同 → 视为可并存（记 `coexist_with`）
- **但任一方是 V0 → condition 不构成并存理由，一律 `needs_review`（必须人审）**
- 队列三选一：`keep-a` / `keep-b` / `keep-both`；败方 → `superseded`，并写 History

---

## 状态与前缀

| 状态 | 在哪 | 含义 |
|---|---|---|
| `active` | `claims/` | 正常可用 |
| `candidate` | `queue/` | 缺 `use_when` 或 V3；只作参考 |
| `pending` | `queue/` | 有冲突待裁决 |
| `needs_review` | `queue/` | 冲突且涉及 V0，必须人审 |
| `refuted` | `claims/` | 已证伪（V4） |
| `superseded` | — | 裁决后退役（旧值保留，可追溯） |

---

## 围栏（写死在规则里，不是建议）

1. **原件不可改**：`inbox/` 写入即不可变，要改就重收一份
2. **V0 只能本人写**；agent 最多给 V2 建议
3. **冲突不静默覆盖**：一律进队列等人裁决
4. **没有 `source_ref` / `verify` 的，不许进 claims**；V3 只进候选区
5. **收工只写「结论 + 依据」**，不写过程
6. **什么不该入库**：文件清单、进度（「已移走 12 项」）、中间草稿、日志 —— 这些归待办/工单

> 原因很简单：库一旦装运行时数据，检索会被日志淹没。

## 为什么是这些闸（每条都对应一次真实踩坑）

| 闸 | 没有它会怎样 |
|---|---|
| 实体必须先登记 | 同一个人出现三种写法，检索全漏 |
| source_ref 可定位 | 结论无法回溯，等于道听途说 |
| 重复判先于冲突判 | 重复被当冲突，队列里全是自己跟自己打架 |
| 规定类要有 dimension | 两件并行的事被判成「同一件事的两种说法」，互相洗掉 |
| use_when | 库变成「发生过什么」的流水账，下次用不上 |
| V3 只进候选区 | 未证实的东西和已证实的混在一起被当依据 |
| V0 人审 | 规则级冲突被「条件不同」自动洗过 |
| 降级只有人能降 | agent 心情一坏就把结论降档，历史不可信 |

---

## 它不做什么

- 不做向量检索、不做 RAG、不接任何模型 —— 它只管**进门那一步**
- 不替你判断内容对不对，只保证：**每条都能被检验、被回溯、被推翻**
- 不绑定任何框架：一个目录 + 一个 Python 3 脚本，零依赖
